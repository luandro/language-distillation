# mzr dataset manifest reconciliation

Status: **Diagnosis historical; code fixed in `5335e00`; the committed dataset files are
still the old run and are being re-sorted before the next export.**

Scope: `exports/mzr/datasets/manifest.json` reports `train_count` 4725 and `synthetic_train_count` 24. `train.hf.jsonl` has 4701 rows. This note records why, and what a corrected manifest says now that the exporter is fixed. This note itself edited nothing under `exports/`; the working tree's dataset files carry the owner's own uncommitted changes.

## Counts (pre-fix run on disk)

| Item | Manifest | Files on disk | Note |
|---|---|---|---|
| train_count | 4725 | 4701 (hf, alpaca, chatml) | Differs by 24 |
| val_count | 543 | 543 (all formats) | Match |
| test_count | 250 | 250 (all formats) | Match |
| synthetic_train_count | 24 | 0 rows with synthetic provenance | 24 clean synthetic phrases exist in `exports/mzr/synthetic_phrases.json` |
| attested_train_count | 4701 | 4701 | Match, but includes harvested train rows |
| harvested_train_count | 30 | n/a (pool-level) | Not separately verifiable in file |
| harvested_val_count | 25 | n/a | Pool-level |
| harvested_test_count | 50 | n/a | Pool-level |

The 4701 `train.hf.jsonl` rows are 4671 with `corpus:*` provenance and 30 with
`harvested:*` provenance. None are synthetic.

## Cause

Code defect, not data and not manual manifest editing.

1. The exporter built `train_pool = h_train + att_train + clean_synth`, and `train_count` /
   `synthetic_train_count` were taken from that pool, so they included the 24 synthetic
   phrases.
2. `_write_hf_nmt`, `_write_alpaca` and `_write_chatml` skipped any item whose target or
   contact side was empty.
3. `_extract_pair` read only `target`, `target_text`, `src` and `portuguese`,
   `reference_text`, `tgt`. Synthetic records use `target_phrase` and
   `portuguese_translation`. Both lookups returned empty, so all 24 synthetic rows were
   dropped at write time.
4. The export did not compare written rows with `len(train_pool)`, so the mismatch was silent.

The manifest checksum for `train.hf.jsonl` (`13b34966...`) matches the file on disk. The
manifest and file come from the same run, so the manifest is not stale or hand-edited. It is
the code that was wrong.

Val and test are unaffected because they contain no synthetic rows.

## Fix (applied in code; dataset not regenerated)

Applied in `5335e00` and covered by `tests/unit/test_synthesis_batch_and_export.py`:

- `_extract_pair` reads `target_phrase` / `portuguese_translation` for synthetic records.
- Every writer returns its row count; the export raises if any file's count differs from its
  pool length.
- A row with an empty side raises instead of being skipped.
- Splits are written to unique temp files and published per file with `os.replace` after the
  count guard, so a failed export no longer truncates a previous good run. The manifest is
  written to a temp file and replaced last; the nine splits and the manifest are still not
  one atomic set, so a crash between replacements can mix runs.
- Harvested test/val rows are selected per provenance source (sorted by ref), so adding a
  new harvested file does not swap an existing source's benchmark.
- A row records one `source_id` per side; a two-source pair keeps only one. A generated
  index and multi-source row lineage are outstanding.
- The manifest reports `rows_without_source_ids`, `run_ids`, and the source-index path/digest, and
  `attested_train_count` no longer double-counts harvested rows (`corpus_train_count` is the
  corpus-only figure).

A production run with the fixed code (written to a temporary directory, with the 105-row
Cesarino harvested file as the only harvested input) produced 4725 / 543 / 250 rows, ids on the
corpus and harvested rows, and a new checksum set. A second harvested file (Wenia, 921 rows)
was added to the repo afterwards, so current totals will be larger. The committed
`exports/mzr/datasets/*` files were **not** regenerated in that commit: the owner is
re-sorting the dataset before the next export. Re-run `langpipe synth export --lang mzr` to
replace them.

Persisted format change: per invariant 11, the manifest shape change is documented here and
tested; `schemas/dataset-manifest.v1.schema.json` is still not implemented, so the manifest
remains an unvalidated dict.

## What the fixed exporter writes now

Do not hand-edit the manifest. Its counts come from the pools, its checksums from the files,
and it is regenerated by the export command. The fields are:

```json
{
  "target_language": "mzr",
  "contact_language": "por",
  "train_count": "<written rows>",
  "val_count": "<written rows>",
  "test_count": "<written rows>",
  "synthetic_train_count": "<clean synthetic rows in the train pool>",
  "attested_train_count": "<corpus rows in train>",
  "corpus_train_count": "<same, explicit>",
  "harvested_train_count": 30,
  "harvested_val_count": 25,
  "harvested_test_count": 50,
  "rows_without_source_ids": "<rows whose provenance resolves to no source/policy id>",
  "test_purity_verified": true,
  "val_purity_verified": true,
  "source_ids": ["<resolved source ids>"],
  "policy_ids": ["<resolved policy ids>"],
  "run_ids": ["<resolved registration runs>"],
  "source_index_path": "var/exports/source_index.json",
  "source_index_sha256": "<digest of the index used>",
  "warnings": ["<non-fatal production-input warnings>"],
  "sha256_checksums": {"<file>": "<sha256>"},
  "output_dir": "exports/mzr/datasets"
}
```

Setting the pre-fix manifest to 4701 by hand would hide the dropped rows instead of fixing
them; that is why the code was fixed instead.
